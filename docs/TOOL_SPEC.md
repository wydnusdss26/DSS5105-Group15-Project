# Track 1 tool specification (defined before implementation)

The manager uses narrow, typed Python tools, not arbitrary SQL or generated code. This accepts a limited question vocabulary in exchange for audited arithmetic, safe filters, and stable evidence. The agent must ask for missing identifiers and decline questions outside these datasets. The model is DeepSeek `deepseek-flash`, using its OpenAI-compatible API.

Every read reloads the CSVs. Results contain computed facts, source file hashes, and source row identifiers; the interface expands the exact source snapshots. A follow-up asking why performs fresh retrieval. Tools never execute text from CSV cells as instructions.

| production_summary / retrieval | Inclusive start/end dates, optional stage | Stage totals and working-day averages with source rows | What did a stage produce? | No attribution to an order or worker | Missing dates disclosed, no interpolation; Sunday zero excluded from working-day rates |
| judge_stage / judgement | Stage, target date, optional hypothetical daily output; baseline_method: prior_28_days / previous_week / same_weekday | Selected judgement and all three comparisons, normal bounds, minimum/actual sample counts, exact sample/missing dates, recent seven-day mean/min/max, source rows, policy version | Is daily output normal relative to a stated baseline? | No causal diagnosis; no statistical confidence claim; never treats a hypothetical quantity as recorded output | Missing target, inadequate/zero baseline -> unknown; Sunday -> closed; invalid method/nonfinite output rejected |
| trace_order / tracing | Exact order ID | Fresh row, risk reasons and explicit rule definitions | Why is this order at risk? | Does not paraphrase old chat as evidence | Unknown ID returns no match |

## Inspectable definitions

- Detailed briefings (`management-briefing-v2`) combine all unfinished orders with each stage's actual yesterday output and three explicit baselines. E3 contains Python-computed order/customer aggregates. Flagged means Overdue or At risk; the share uses all unfinished orders as denominator. Due-soon means 0–7 calendar days inclusive. Inactive and due-soon groups overlap risk groups. Quantities are full order sizes, not remaining work.
- Priority orders: overdue first, earliest due date, longer inactivity, then order ID; show eight and disclose how many additional flagged orders were omitted. Customer exposure: overdue count, flagged count, flagged share descending, then customer name; show five. Evidence contains all flagged customers. Four stage outputs are never summed into a finished-goods total.
- The briefing model writes only the English executive overview; detailed sections, tables, baseline comparisons, limitations, and conditional recommendations remain deterministic. Recommendations require a separate confirmed action to take effect. Earlier saved briefings remain unchanged; Preview briefing generates the latest format.

- Risk retains the original dashboard rules: overdue before the reference date; otherwise due within seven calendar days inclusive or inactive for at least three Monday–Saturday days. Completed orders excluded.
- Normal output (`stage-output-v2`): arithmetic mean of the explicitly selected baseline. `prior_28_days` (default) uses available Mon–Sat observations in the preceding 28 calendar days, minimum 12 samples; `previous_week` uses the previous complete Monday–Saturday week, minimum 3 samples; `same_weekday` uses the target weekday in each of the preceding four weeks, minimum 3 samples. Sundays and the target date are excluded. All comparisons are returned so disagreement is visible, but the user-selected method determines the primary label. These minimum counts and ±20% thresholds are inspectable design choices, not requirements imposed by the course or statistically estimated confidence limits.
- Low means output <80% of the unrounded mean; high means >120%; endpoints are normal. Tool returns rounded normal bounds, exact sample dates, missing dates, actual/expected/minimum counts, and the formula. Zero mean or insufficient samples produces unknown. A hypothetical daily quantity is explicitly marked; no date supplied in chat means an explicitly stated reference-date assumption, not an actual production record. Shift/hour/week quantities need clarification.
- Recent trend is a separate trailing-seven-calendar-day working-day summary. Its minimum, maximum and mean are computed in Python, not inferred by the LLM from rows. For ASSEMBLY on 2026-04-01 with a hypothetical 800 pieces/day: default mean 702.38, +13.9%, normal range 561.90–842.85; recent six workdays mean 425.5, range 394–464. Previous complete week is March 23–28, not March 25–31.
- Internal estimate: mean stage rates from the latest 28 calendar days before the reference date; all unfinished pieces at the current stage and every later stage count as backlog. Sum `(backlog + new pieces) / stage rate` over all four stages, round up, then advance Monday–Saturday days starting after today. Deliberately conservative serial processing, no partial progress or overlap assumed.
- Workshop estimate: `ceil(queue working days + pieces / capacity)` Monday–Saturday days after today, plus pickup transport in calendar days. Sunday arrivals roll to Monday. No defect retry estimate: the dataset has a batch defect probability but not the fraction redone. Show probability separately.
- New orders use full-batch workshop eligibility; a trial batch cap never disappears by implicit splitting. Currency is unspecified; costs are dataset units, not dollars.

## Actions, autonomy and blast radius

The LLM can only propose. An explicit Confirm button stores the exact reviewed payload and an audit row atomically in local SQLite, using the proposal ID for idempotency. Reject discards it. No tool sends email or chat, edits source CSVs, executes code, or commits a capacity reservation. The maximum effect is one local note/draft/reminder/watch or a schedule change. Watch cancellation also requires confirmation.

A separate worker polls every 30 seconds, including when the browser is closed. Only confirmed watches and schedules run. An order watch fires once at its deadline if stage and last-activity date are unchanged and the order is unfinished; stage watches compare fresh output at their deadline and disclose missing observations. Notifications appear in the in-app inbox, not OS push/email. Unchanged checks do not generate repeated alerts. Briefings are saved once per business date after the configured local time; failed generation remains visibly marked for retry.

The simulation clock starts on 2026-04-01 and advances one business date per real calendar day (including Sundays as dates). Wall-clock schedule times use Asia/Shanghai. The UI displays both clocks. CSV dates do not advance automatically: after the provided history ends, tools report missing observations instead of treating absent production as zero.
